# 3. Распознавание, курсы и денежные расчёты

С 04.11.2026 эти правила применяются к SPA/PWA. В браузерном прототипе OCR выполняет Tesseract.js, а локальные данные хранит IndexedDB. Окно потери цены для начальной проверки изменено на 3 секунды. Денежные правила перенесены. Отличия и ограничения описаны в [документе 9](09-web-app.md).

Версия 0.1 · 03.11.2026. Документ конкретизирует разделы 3, 5, 7–9 исходного ТЗ. Правила, отсутствующие в исходнике, — **предложения v0.1**, в том числе пороги стабильности, давности и сохранения истории.

## 3.1. Что должен выдавать анализ кадра

Не просто первое число из OCR, а список кандидатов с нормализованной суммой RON, областью изображения, валютным маркером и контекстом. Контекст включает соседние слова, относительный размер текста, возможную единицу измерения и признаки старой/условной цены. Имена товаров не распознаются как отдельная продуктовая функция.

Последовательность:

1. Получить текстовые блоки и координаты из локального OCR.
2. Найти числовые фрагменты и близкие `RON`, `LEI`, `lei` без учёта регистра.
3. Нормализовать число по правилам ниже. Неоднозначный формат оставить кандидатом для проверки.
4. Привязать число к одной этикетке и локальному контексту, не соединяя соседние ценники.
5. Отделить проценты, массу, объём, даты, штрихкодовые цифры, старые, условные и удельные цены.
6. Выбрать основную цену или вернуть неоднозначность.
7. Стабилизировать выбор между кадрами, затем пересчитать и показать.

OCR сам по себе не определяет, какая цена актуальна. В частности, наличие зачёркивания нельзя считать гарантированно доступным полем текстового SDK: если контекста недостаточно, нужен визуальный анализ либо явное подтверждение. Не обещать автоматический выбор сложной акции до проверки прототипом.

## 3.2. Правила разбора чисел

Внутреннее значение исходной цены — целое число **банов**: `24,99 RON → 2499`. Одному RON соответствует 100 банов. Для OCR поддержать:

| Текст | Результат | Условие |
|---|---|---|
| `24,99 RON` | 2499 банов | Запятая — десятичный разделитель |
| `24.99 RON` | 2499 | Точка с двумя цифрами справа — десятичный разделитель |
| `1.299,00 RON` | 129900 | Точки — группы тысяч, запятая — дробь |
| `1 299,00 LEI` | 129900 | Пробел/неразрывный пробел — корректная группа тысяч |
| `15,99` | 1599 | Принять RON по умолчанию, отразить предположение |
| `24 LEI` | 2400 | Целое число с валютой |
| `24,9 RON` | 2490 | Один десятичный знак дополняется нулём |
| `0,99 RON` | 99 | Ведущий ноль сохраняется |
| `0,00 RON` | 0 | Нулевая цена допустима только после подтверждения как необычная |
| `1.299 RON` | Не подтверждать автоматически | Возможна потеря разделителя/дроби; предложить проверку значения |
| `1299` | Не подтверждать автоматически | Голое целое может оказаться артикулом |
| `24 99` | Не объединять только по строке | Возможно соединение целой и дробной части только по геометрии одной цены |
| `-20%`, `500 g`, `1 L`, дата, длинный штрихкод | Не цена | Исключить по контексту |
| `24,99 EUR` | Не пересчитывать как RON | Явная другая валюта не заменяется валютой по умолчанию |
| `12,3456`, `1.29,00`, буквы вместо цифр | Невалидно/нужна проверка | Не угадывать значение |

Форматы с группировкой принимаются только при правильных группах из трёх цифр. Нельзя просто удалить все точки и запятые. Разделитель с одной/двумя цифрами справа считается дробным, если остальная группировка корректна. Смешанный формат `1,299.00` в MVP автоматически не принимается; допускается ручное исправление.

Целая и дробная части на разных строках/разным кеглем встречаются на реальных ценниках. Их объединение разрешается только в пределах одной этикетки, при согласованных координатах и устойчивости нескольких наблюдений. Проверить такие примеры до обещания поддержки конкретной сети магазинов.

Символы `O/0`, `I/1`, `S/5` автоматически глобально не заменять. Сомнительное чтение вести к подтверждению. Не округлять OCR-число с тремя дробными знаками до цены.

Для ручного ввода действует более простое правило из документа 2: неотрицательное число без групп тысяч, с 0–2 дробными знаками. Ввод не обязан содержать `RON`. Сумма `0` требует явного подтверждения необычной цены.

## 3.3. Выбор цены на этикетке

Приоритет — **текущая обычная основная цена товара**. Нельзя выбирать просто минимум, максимум, самый крупный шрифт или ближайшее к центру число без проверки контекста.

| Ситуация | Правило v0.1 |
|---|---|
| Одна валидная цена с RON/LEI | Основной кандидат |
| Цена без валюты | RON по умолчанию; подпись «RON по умолчанию», проверка контекста всё равно обязательна |
| Основная и мелкая `/kg`, `/l`, `lei/kg` | Основная в приоритете, удельная не подменяет её |
| Есть только удельная цена | Показать как `RON/кг` или `RON/л`; сохранить единицу при конвертации, запросить подтверждение |
| Явно старая/зачёркнутая и текущая цена | Исключить старую, выбрать текущую; при ненадёжном различении — подтверждение |
| Акция без дополнительных условий | Выбрать текущую акционную, если роль надёжно определена |
| Цена по карте/при покупке нескольких единиц и обычная | Обычная — автоматический результат; условную дать выбрать с предупреждением, если условие распознано |
| Несколько цен, условия неясны | Показать выбор, не объявлять одну достоверной |
| Несколько этикеток | Анализировать ближайшую к центру, только если её границы и цена однозначны; иначе попросить навести на одну |
| Явная EUR/UAH/другая валюта | Не применять коэффициенты для RON; сообщить «Поддерживается цена в RON» |

Правила условной и удельной цены добавлены сверх исходника. Без уверенного определения типа лучше запросить подтверждение. Конвертация цены за килограмм остаётся ценой за килограмм: количество товара и итог на кассе приложение не рассчитывает.

На этапе прототипа использовать простые проверяемые правила текста и расположения. Специальный детектор зачёркивания или OpenCV добавлять только при подтверждённой необходимости; если без него обязательная приёмка не проходит, это отдельная задача, а не скрытое снижение качества.

## 3.4. Стабильность между кадрами

Предлагаемые начальные параметры для прототипа:

- Не более **5 запусков OCR в секунду**, не больше одного выполняющегося запроса. Пока он занят, поступающие кадры пропускаются.
- Два последовательных обработанных наблюдения одного значения, единицы и близкой области подтверждают стабильность, если нет смысловой неоднозначности. Стабильная неправильная цифра всё ещё возможна — качество проверяется отдельно.
- Изменение выбранной суммы, единицы, этикетки или потеря области сбрасывает подтверждение. Один шумный кадр не должен немедленно заменить устойчивую карточку случайным числом.
- При отсутствии подтверждённого наблюдения прежней цены более **1 с** убрать старую карточку. Пока идёт ожидание, пометить её «Ищем цену…».
- Остановка сканера, смена камеры и уход в фон немедленно сбрасывают кандидат и рамку.

Для сравнения областей можно начать с пересечения прямоугольников (IoU ≥ 0,5) с учётом преобразования координат. Это инженерная гипотеза для настройки по данным, не требование продукта. Сильный сдвиг рамки начинает новое событие, даже при одинаковой сумме.

Статусы результата: `searching / checking / stable / needsConfirmation / fixed`. Не строить индикатор на универсальном пороге OCR-confidence: доступность и смысл этого поля нужно проверить у выбранного SDK/моста на обеих платформах. Смысловая неоднозначность всегда важнее числовой уверенности OCR.

## 3.5. Контракт курсов и формулы

Внутри приложения хранить коэффициенты в одном направлении:

```text
eurPerRon = количество EUR за 1 RON
uahPerRon = количество UAH за 1 RON

priceRon = amountBani / 100
priceEur = priceRon × eurPerRon
priceUah = priceRon × uahPerRon
```

Имена `RON/EUR` из исходника могут трактоваться по-разному, поэтому в коде и данных использовать однозначные имена `eurPerRon`, `uahPerRon`. Коэффициенты — положительные конечные десятичные числа, сохраняемые десятичными строками без сокращения до точности отображения.

Если API выдаёт значения `qC = количество валюты C за 1 B` для общей базы B:

```text
eurPerRon = qEUR / qRON
uahPerRon = qUAH / qRON
```

Если источник выдаёт RON за единицу целевой валюты, нужен обратный коэффициент. Если котировка дана за 100 единиц, сначала привести её к одной единице. Направление, базовая валюта и множитель проверяются тестом конкретного адаптера API.

Денежные расчёты выполнять десятичной арифметикой или эквивалентной рациональной арифметикой без ошибок двоичного `double`. Для деления, создающего бесконечную дробь, задать документированную точность нормализации, предлагаем **12 знаков после запятой**. Не округлять цену или произведение до финального форматирования; способ нормализации фиксируется у адаптера и тестируется.

Округление отображаемой конвертации: **half-up** до выбранных 0 или 2 знаков. RON показывается с двумя знаками. Историческая сумма хранится до форматирования, поэтому настройка видимости/точности не меняет исходные данные.

Все числа далее — **тестовые**, не рыночные котировки:

| RON | EUR за 1 RON | UAH за 1 RON | EUR, 2 знака | UAH, 2 знака |
|---|---|---|---|---|
| 24,99 | 0.2 | 10 | 5,00 | 249,90 |
| 1299,00 | 0.2 | 10 | 259,80 | 12 990,00 |
| 0,10 | 0.2 | 10 | 0,02 | 1,00 |
| 0,05 | 0.1 | 10 | 0,01 | 0,50 |

Последняя строка проверяет `0,005 EUR → 0,01`, а при нулевой точности `0,50 UAH → 1`. Тест кросс-курса: при `qRON=5`, `qEUR=1`, `qUAH=50` получить `0.2` и `10`.

## 3.6. Получение и кэширование курсов

В версии 0.2.0 используется открытый ExchangeRate-API. Запрос по базе RON возвращает количество EUR и UAH за 1 RON, поэтому инверсия и кросс-курс не требуются. Коэффициенты поступают в денежный расчёт как десятичные строки. При отсутствии курса интерфейс показывает только цену RON. Тестовые значения доступны в отдельно включаемом debug-режиме. [Документация открытого API](https://www.exchangerate-api.com/docs/free).

Для принятия ответа API требуются оба коэффициента, известная база, корректные единицы, источник и дата данных. Нулевые, отрицательные, бесконечные, отсутствующие или противоречивые значения отклоняются. Ответ с датой данных явно из будущего также не заменяет кэш; правила допустимого времени/часового пояса уточняются по контракту поставщика. Отсутствие даты данных не маскировать временем запроса.

Сохранять **единый снимок** EUR/UAH атомарно. Нельзя смешивать свежий EUR со старым UAH и выдавать их за одно обновление. Ошибка обновления не удаляет последний корректный снимок.

Предлагаемая политика:

1. На запуске/возврате приложения использовать кэш немедленно.
2. Начинать автоматическое обновление при отсутствии кэша либо если после успешного получения прошло ≥ 1 ч и наступило время следующей публикации, если источник сообщил его. Между автоматическими попытками выдерживать минимум 1 ч, в том числе после перезапуска. Источник обновляет котировки раз в день. [График и лимиты открытого API](https://www.exchangerate-api.com/docs/free).
3. Ручное «Обновить» разрешено независимо от автоматического интервала; пока запрос выполняется, повторная кнопка недоступна.
4. Один активный запрос, тайм-аут **10 с**. Ошибка завершает попытку с сообщением, без бесконечного цикла повторов.
5. Данные старше **24 ч по дате источника** помечать «Курс устарел», но продолжать разрешать пересчёт с явной датой. Предельный срок блокировки не задан.
6. При обновлении курса текущая автоматическая карточка пересчитывается по новому снимку. Зафиксированная/открытая на подтверждение карточка и история сохраняют прежний снимок. Следующее событие использует новый.

Дата данных (`dataAsOf`) и время получения (`fetchedAt`) — разные поля. Если источник публикует только дату, показывать именно дату; порог давности считать от начала этой даты в часовом поясе источника, зафиксированном адаптером. В выходные предупреждение о давности допустимо: оно не означает ошибку API. Конкретный порог может измениться после выбора расписания поставщика.

Состояние «без сети» относится к результату запроса/известной недоступности сети; приложение не должно ошибочно называть любой HTTP-сбой отсутствием интернета.

## 3.7. История без дубликатов видеокадров

Предложение: сохранять **события распознавания**, а не кадры и не товары.

- При переходе нового события в `stable` автоматически создать одну запись, даже если часть целевых валют выключена в UI.
- Пока тот же ценник удерживается в кадре, новые записи не создавать. Ключ — идентификатор текущего события, а не только сумма.
- Новое стабильное значение/единица в той же области либо новая область после потери/сдвига начинают новое событие. После исчезновения цены на ≥ 1 с та же сумма может создать новую запись.
- Два товара с одинаковой ценой, плавно сменившие друг друга без заметного разрыва, могут быть объединены: MVP не идентифицирует товары. Пользователь может зафиксировать новую запись вручную. Это известное ограничение, не корзина.
- Кандидат `needsConfirmation` до подтверждения не попадает в историю. Подтверждение создаёт запись; исправление уже записанного текущего события обновляет её по ID, не добавляя вторую.
- Повторная фиксация уже записанного текущего события не создаёт дубль. Отдельный ручной ввод без связанного события создаёт новую запись.
- При обновлении API не переписывать исторические суммы/курсы. История — снимок на момент события.
- Без курса сохранять RON с пустыми EUR/UAH и статусом `unavailable`. Позднейшее получение курса не заполняет их задним числом.
- Лимит — **100 записей**, удалять самые старые при вставке сверх лимита. Удаление истории — одна операция, не затрагивающая кэш и настройки.

Точное поведение события нужно проверить на проходе по полке. Не вводить распознавание товара, облачную синхронизацию и сложный трекинг ради дедупликации MVP.
