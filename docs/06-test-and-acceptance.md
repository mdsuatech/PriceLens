# 6. Проверка и приёмка

С 04.11.2026 приёмка относится к SPA/PWA. Правила цен и расчётов сохраняют силу. Нативные SDK и SQLite заменены браузерной камерой, Tesseract.js и IndexedDB. Дополнительно проверяются перезагрузка без сети, загрузка OCR из кэша, установка PWA и размещение в подкаталоге GitHub Pages. Текущие проверки описаны в [документе 9](09-web-app.md).

Версия 0.1 · статус обновлён 03.11.2026. Это **план приёмки полного MVP**. Текущий прототип и уже выполненные проверки описаны в [отчёте](08-prototype-status.md); они не заменяют приёмку на реальных ценниках. Целевые задержки до 1 с взяты из ТЗ; размеры выборок, процентили и пороги качества ниже — предложения v0.1 (D-07).

## 6.1. Набор реальных ценников

Предлагается собрать минимум **120 разных сцен**: 60 для разработки/настройки, 60 для отдельной приёмки. Не считать соседние кадры одного ценника независимыми сценами. Охватить реальные ценники Lidl, Kaufland и Carrefour при возможности; до проверки не заявлять универсальную поддержку сети.

Приёмочные 60 сцен:

| Класс | Количество | Что включить |
|---|---|---|
| Обычные | 30 | Одна основная цена; точка/запятая, RON/LEI/без валюты, разные размеры, обычный наклон |
| Сложные | 20 | Старая + текущая, акционная/условная, удельная, разделённая дробь, несколько цен/этикеток, наклон/свет сложнее обычного |
| Отрицательные | 10 | Нет цены, только скидка/масса/дата/штрихкод, другая валюта, текст без цены |

Каждой сцене присвоить ID, записать правильную цену, валюту, единицу, тип цены и ожидаемое поведение: автоматический результат / подтверждение / отсутствие результата. Разметку сложных случаев проверить человеком до тестирования. Из 20 сложных сцен минимум 10 должны допускать однозначный автоматический ответ; остальные включают случаи обязательного подтверждения по правилам продукта.

Если сохраняются тестовые фото/видео, получать их отдельно для разработки с разрешённым использованием, без лиц и персональных данных. Это тестовые материалы, а не скрытое сохранение кадров приложением. Их загрузка в тестовый harness не означает появления функции галереи в MVP.

Дополнительно записать короткие проходы камерой по нескольким этикеткам: разные суммы, одинаковые суммы на разных товарах, удержание одного ценника, потеря и повторное появление. Статичные изображения не подтверждают качество live-сценария.

## 6.2. Порог качества выбора цены

Предлагаемая приёмка на отдельном наборе из 60 сцен:

- Обычные сцены: минимум **29 из 30** дают правильную автоматическую цену и единицу. Отсутствие результата и ручная проверка считаются пропуском автоматического распознавания.
- Из 20 сложных сцен заранее разметить, где автоматический ответ вообще допустим. На подмножестве однозначных сложных сцен минимум **80%** должны давать правильный автоматический ответ; округлять необходимое число успехов вверх.
- В неоднозначных сложных сценах обязательны подтверждение/выбор. На приёмочном наборе — **0 неверных результатов со статусом «Стабильно»** и 0 подмен старой/удельной/условной цены обычной основной.
- В 10 отрицательных сценах — **0 автоматических цен**. Иная валюта не пересчитывается как RON.
- Правильность значит точное совпадение суммы в банах, единицы и требуемого типа цены; «похожая сумма» не засчитывается.

Публиковать одновременно автоматическую полноту, число неверных уверенных результатов, число запросов подтверждения и пропусков по каждому классу. Одно высокое число «точность OCR» не показывает качество выбора основной цены. Нулевые ошибки в небольшом наборе не являются гарантией для любых магазинов.

Приёмочный набор заморозить перед оценкой. После исправления по его примерам такие сцены становятся регрессионными; для независимой финальной оценки добавить новые сцены и явно указать размер выборки. Пороги нельзя молча снижать.

## 6.3. Устройства и производительность

Предварительная матрица: минимум один реальный Android умеренной производительности, один более современный Android и один реальный iPhone. Для каждой заявленной минимальной версии ОС нужен реальный тест либо явное сужение списка поддержки. Модели, ОС, SDK и версии пакетов зафиксировать до приёмки; эмулятор не заменяет тест камеры.

Нормальные условия: ценник виден целиком, сфокусирован, без сильного блика/смаза; размер цифр достаточен для выбранного разрешения. В отчёте записать освещение, примерный размер/дистанцию и условия, чтобы «нормально» не означало произвольное удобное окружение.

Для каждого устройства — не менее 30 независимых попыток первого распознавания и 30 смен цены. Использовать release/profile, не оценивать производительность только по debug.

| Показатель | Начало → конец | Цель |
|---|---|---|
| Первичное распознавание | Первый пригодный кадр с ценой после готовности preview → стабильная карточка | p95 ≤ 1 с |
| Смена ценника | Первый пригодный кадр нового ценника → новая стабильная карточка | p95 ≤ 1 с, ориентир 0,5–1 с из ТЗ |
| Задержка расчёта/отрисовки | Готовность стабильной цены → видимый пересчёт | Измерить отдельно; сетевого ожидания нет при наличии кэша |
| Исчезновение | Последнее подтверждённое наблюдение → удаление старой карточки | ≤ 1 с по предложению D-06 |
| Запуск приложения | Открытие → preview | Измерить отдельно; не скрывать внутри метрики OCR |

Расчёт p95: сортировать длительности и брать значение с рангом `ceil(0.95 × N)`. Тайм-ауты/пропуски не исключать: считать неуспешными попытками, сообщать отдельно и включать как превышение порога. Метрики показывать по каждому устройству, не усреднять медленное устройство с быстрым.

Отдельный 15-минутный прогон live-сканирования: нет падений, накопления кадров, исчерпания памяти или системной остановки камеры из-за перегрева. Проверить, что одновременно выполняется максимум один OCR, в фоне OCR не запускается, после возврата камера восстанавливается. Записать потребление памяти, CPU, батареи и температуру/thermal state, если доступны. Числовой бюджет батареи в ТЗ не задан: определить его после базового замера, а не обещать непроверенное значение.

## 6.5. Какие проверки автоматизировать

**Unit:** парсер и локали, контекст и выбор кандидата на текстовых/геометрических fixtures, стабилизация и устаревание результата, арифметика/кросс-курсы/округление, валидация API и политика давности. Управлять временем через подменяемые часы, не заставлять тесты ждать реальные часы.

**Интеграционные:** атомарное сохранение кэша, неизменность исторического снимка, дедупликация события, лимит и очистка истории, настройки и миграции. HTTP подменять для воспроизводимых ошибок; отдельно проверить реальный контракт выбранного поставщика.

**UI/на устройстве:** разрешения, текст и действия состояний, исправление, камера/рамки, фон/возврат, поток и скорость. Автоматизация не заменяет проверку реальных сложных этикеток.

Не писать тесты ради создания тестовых файлов. Каждый тест должен защищать требование, риск или воспроизведённую ошибку.

## 6.6. Условия готовности

MVP готов, когда:

- Все F-01…F-14 выполнены и есть результаты соответствующих сценариев; N-01…N-06 проверены в согласованной матрице.
- Пройден независимый набор ценников и live-проходы, с отчётом качества и задержек по устройствам.
- Нет известных падений, неверного направления курса, потери истории или уверенного выбора неверной цены в обязательных контрольных случаях.
- Доступны реальные release-сборки обеих заявленных платформ и инструкция воспроизведения сборки.
- Курсы production не являются демонстрационными; источник/дата показаны; автономный режим проверен.
- Соблюдена локальная обработка кадров, проверены разрешения, SDK и фактические сетевые обращения.
- Оставшиеся ограничения описаны, а спорные решения для релиза закрыты владельцем продукта.

Форма отчёта для каждого прогона: дата, commit/версия сборки, ОС/устройство, версии зависимостей, версия набора, результаты T-xx, метрики по классам, p95, найденные дефекты и итог. До появления реализации отмечать «не проверено», а не «пройдено».
